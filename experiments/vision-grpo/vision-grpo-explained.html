01在第 2 章上加一张图

第 2 章：一道 GSM8K 数学题，纯文本，答案是数字。 第 3 章：一道 GeoQA 几何题，题目 + 一张图，答案是 A/B/C/D 四个选项之一。

GRPO 的骨架完全没变。变的只有两件事：

变化一

输入多了一个模态

文本 token 之外，还有一张图片被编码成视觉 token。 两者拼在同一条序列里，模型一次 forward 同时看到。

变化二

reward 变成选项匹配

不再比较数字，而是从回答里抠出 \boxed{A} 到 \boxed{D}， 和正确选项比。因此多了一个指标 format_rate。

所以这一页的重点不是"再讲一遍 GRPO"，而是视觉输入这条支线， 以及它带来的两个新问题：模型写不完答案、以及所有组都退化。

和上章共用的部分

generate_group()、sequence_policy_loss()、group_advantages() 全部原样复用。第 3 章的 local_gpu.py 只改了输入构造和打分函数， 训练循环的 5 个步骤一行没动。

02图片怎么变成 token

这是本章唯一真正新的机制。传统做法要手动切图、算 patch、拼占位符， 但 Transformers 的 AutoProcessor 把这些都包好了。

一张 RGB 图 PIL.Image
+
题目 + 四选项 纯文本
→
AutoProcessor apply_chat_template

调用只需要一次，返回的字典里同时装着文本和视觉张量：

experiments/vision-grpo/local_gpu.py · build_messages() + apply_chat_template()

messages = [{
    # 关键：content 是一个列表，图片和文本并列
    "role": "user",
    "content": [
        {"type": "image", "image": image},
        {"type": "text",  "text": format_question(subject, choices)},
    ],
}]

inputs = processor.apply_chat_template(
    messages,
    tokenize=True,
    add_generation_prompt=True,
    return_dict=True,
    return_tensors="pt",
)

# 返回的字典大概长这样：
inputs["input_ids"]        # 文本 token，含视觉占位符
inputs["attention_mask"]   # 哪些位置要参与注意力
inputs["pixel_values"]     # 图片切成的 patch 张量
inputs["image_grid_thw"]   # 每个 patch 的网格尺寸

关键点是 input_ids 里已经有视觉占位符。 图片不是"另外塞进去"的，而是被展开成一串特殊 token 嵌在文本序列里。 模型 forward 时，这些占位符的位置会被 pixel_values 的内容填充。

为什么这很重要

因为这意味着视觉 token 和文本 token 共用同一套位置编码。 所以 completion 的起点仍然可以用 len(input_ids) 算出来， 第 2 章那个 prompt_length - 1 的切片逻辑完全不用改。

原版 PyTRIO 要手动算 expected_tokens 去和远端对齐， 本地版因为 processor 和模型是同一套实现，不需要这个检查。

图片从哪来

GeoQA 的 parquet 里，图片有两种存法：PIL 对象，或者 {"bytes": ...}。 as_rgb_image() 把两者统一转成 RGB，因为模型只接受三通道。 

def as_rgb_image(value):
    if isinstance(value, Image.Image):
        return value.convert("RGB")
    if isinstance(value, dict):
        value = value.get("bytes") or value.get("image")
    return Image.open(io.BytesIO(value)).convert("RGB")

03训练循环的差异

五步骨架和第 2 章一样。下面只标出不一样的地方，没标的行就是原样复用。

1

取一行，解出图片L99–104新增

row["image"] 转 RGB，row["label"] 转成 A/B/C/D 当标准答案。 然后 build_messages() 把图和题拼成一条消息。

2

采样 4 条回答L106

和第 2 章同一个 generate_group()。 区别只是输入里多了 pixel_values，模型在生成时能"看见"图。

3

抠选项打分L118–120新增

extract_choice() 找最后一个 \boxed{A-D}， 和 gold_choice 比。找不到 boxed 就记 None，reward = 0。

4

保留视觉张量给训练用L123–127新增

vision_inputs 从 inputs 里挑出 pixel_values 这些非文本字段，挂到 Sample.extra_inputs 上。 训练 forward 时它们会一起传进模型。

5

loss + backwardL145–158

完全复用第 2 章。唯一的细节：sequence_policy_loss() 会把 extra_inputs 一起塞进 model(**kwargs)， 所以图文 forward 和采样时的条件一致。

新增的指标：format_rate

format_rate = 有 boxed 选项的回答数 / 4。 它和 reward 是两个不同的东西：

format_rate = 0：模型没写出 \boxed{}，格式不对。
format_rate = 1 但 reward = 0：格式对，但选错了。

分开看才知道问题出在"写不出来"还是"想错了"。

04真实一组：平行四边形

run-20261108-184536 第 1 步，题目 id 9286，标准答案 D。 这是本章最干净的一组——4 条回答全部正确。

GeoQA · step 1 · id 9286

平行四边形 ABCD 中，∠B 比 ∠A 大 40°，求 ∠D 的度数。

标准答案 D · 110°

✓ 对 answer 0 reward 1.0 advantage 0.0
在平行四边形ABCD中，我们知道： - 对边平行：AB ∥ CD，AD ∥ BC - 邻角互补：∠A + ∠B = 180° - 对角相等：∠A = ∠C，∠B = ∠D 题目给出：∠B 比 ∠A 大 40°，即 ∠B = ∠A + 40°。 又因为邻角互补： ∠A + ∠B = 180° ∠A + (∠A + 40°) = 180° 2∠A + 40° = 180° 2∠A = 140° ∠A = 70° 那么 ∠B = 70° + 40° = 110° 由于在平行四边形中，对角相等，所以： ∠D = ∠B = 110° 因此，正确答案是 D. 110°。 \boxed{D}
✓ 对 answer 3 reward 1.0 advantage 0.0
... ∠A = 70°，所以 ∠D = ∠A = 70°？不对，这是错的！ **注意！** 在平行四边形中，**对角相等**，即 ∠A = ∠C，∠B = ∠D。 所以 ∠D = ∠B = 110°。 验证：∠A = 70°，∠B = 110°，70 + 110 = 180°，符合邻角互补。 ∠D = 110°，∠C = 70°，也满足对角相等。 所以，∠D = 110°。 最终答案是：\boxed{D}
这一组的 advantage 全是 0

4 条全对，reward 都是 1，均值也是 1，所以每条 advantage = 1 − 1 = 0。 没有相对好坏，就没有训练信号。 代码在第 131 行 continue 掉全部样本，train_samples = 0。

这是本章 10 步的共同结局——每一组要么全对、要么全错， 从来没有出现过"部分对部分错"的组。

值得注意的是 answer 3：它中途写了一句 "所以 ∠D = ∠A = 70°？不对，这是错的！"， 然后自我纠正到正确结论。这种自我纠错后答对的轨迹， 恰恰是 GRPO 最想强化的——但前提是组里有别的样本答错，才有对比。

05512 token 截断

这是本章最值得注意的现象。max_new_tokens=512 是硬上限， 模型生成到这里会被强制切断——不管推理有没有结束。

规律非常干净：tokens 打到 512 的 5 个步，boxed 全是 0；没打满的 5 个步，boxed 全是 4。 没有一个例外。

截断现场

step 5 的一道圆题，答案应该写 60°。这是第 3 条回答的最后部分——推理已经算出 60° 了， 但还没来得及写 \boxed{} 就被切断了：

✂ 截断 step 5 · answer 2 512 token reward 0.0
... 在△ADC中： ∠ACD = 90°， ∠ADC = 30° （刚才推出） 所以 ∠CAD = 180° - 90° - 30° = 60° 所以答案是 **60°** 也可以这样想： 因为AD是直径，所以∠ACD = 90°（直径所对的圆周角） ∠ABC = ∠ADC = ▌
它其实答对了，但拿不到分

这条回答算出了 60°，也就是正确答案。但因为截断发生在写 \boxed{} 之前， extract_choice() 找不到选项，返回 None，reward 记 0。

所以 format_rate = 0 的这 5 步，不能简单理解成"模型不会做"。 其中一部分是"会做，但话太多"。

这也解释了为什么 step 0、5、6、8、9 的耗时都是 49–50 秒， 而答完的步只要 20–42 秒——生成到上限是最慢的情况。

0610 步全是退化组

第 2 章 10 步里有 1 步产生了梯度。这一章是 0 步。 原因比第 2 章更纯粹：4 条回答的 reward 永远完全相同。

stepreward 分布train_samples为什么
0[0, 0, 0, 0]0全被截断，都没写 boxed
1[1, 1, 1, 1]0全对
2[1, 1, 1, 1]0全对
3[1, 1, 1, 1]0全对
4[1, 1, 1, 1]0全对
5[0, 0, 0, 0]0全被截断
6[0, 0, 0, 0]0全被截断
7[1, 1, 1, 1]0全对
8[0, 0, 0, 0]0全被截断
9[0, 0, 0, 0]0全被截断

注意 没有一行是 [1, 0, 1, 0] 这种混合分布。 这不是巧合，是本章的核心结构性原因：

为什么视觉题更难出现混合组

第 2 章的答案是自由数字，4 条采样可以各自算错成不同值，容易分化。 第 3 章只有 4 个选项，模型一旦读懂了图，4 条基本都会选同一个—— 采样温度 1.0 带来的多样性，不足以让它在 4 个选项之间摇摆。

再加上 512 token 的截断是确定性的：题目一难，4 条会同时撞上限， 同时拿 0 分。两种机制都指向同一个结果——组内没有方差。

所以这一章诚实的结果是：训练循环跑通了，但在这 10 步里没有产生任何学习。 这不是 bug，是配置（题目难度、group_size、token 上限）和这个模型能力共同决定的。

07工程：先预检再下载

本章的执行顺序和第 2 章刻意不同。第 2 章是先下载模型再加载数据， 第 3 章反过来——先确认数据可用，再花时间下载 8GB 模型。 

bash scripts/run_modelscope.sh chapter 03
  │
  ├─ 1. 预检 GeoQA（HF 镜像）
  │     ├─ 下载 data/*.parquet
  │     ├─ 过滤 original_split == "train"
  │     └─ 检查每行有 image + 4 个 choices
  │     ↓ 失败就写 data_unavailable，不下载模型
  │
  ├─ 2. 下载 Qwen3-VL-4B-Instruct（约 8GB）
  ├─ 3. 4-bit QLoRA 加载
  ├─ 4. for step in range(10):   ← 图文采样 → 打分 → loss
  └─ 5. 保存 adapter + 同步记录
为什么先预检

省下 8GB 下载

HF 数据源可能连不上、字段可能变、图片可能解不开。 这些都在下载模型之前检查，失败就立刻停。

状态机

data_unavailable ≠ failed

数据不可用是一种合法结局，不是错误。 章节状态记成 data_unavailable，runner 不会把它算成失败。

诚实性约束

绝不用文本数据顶替

代码里写死了：GeoQA 拿不到就记 data_unavailable， 不会偷偷换成 GSM8K，也不会伪造一个成功结果。

实际结果

3503 行通过预检

data_preflight.json 记录了通过的行数。 本次预检成功，才继续下载模型。

09踩过的坑

本章在服务器上留下了一条完整的失败轨迹。下面每一条都能在 results/ 的某个 run 目录里找到原始证据。

① HF 连不上，数据预检失败

证据：run-20261108-182013/data_unavailable.txt

LocalEntryNotFoundError: ConnectError: [Errno 101] Network is unreachable

修法：默认 HF_ENDPOINT=https://hf-mirror.com。 国内 GPU 机器基本都连不上 huggingface.co。

② processor 没有 eos_token_id

证据：run-20261108-182408/error.txt

AttributeError: 'Qwen3VLProcessor' object has no attribute 'eos_token_id'

原因：Qwen3VLProcessor 是个包装器， 真正的 tokenizer 藏在 .tokenizer 里。

修法：加一个 text_tokenizer()，遇到 processor 就自动拆包。 这个坑只在视觉章节出现，第 2 章用的是纯 AutoTokenizer，不会有。

③ 128 token 全部截断

证据：run-20261108-182859 和 183451， 两个 smoke run 的 4 条回答全部 128.0 token，format_rate 全 0。

原因：几何题需要写完整推理，128 token 连题目重述都不够。

修法：full profile 提到 512。但 512 仍然不够—— 5 个步照样撞上限。

这个坑和训练模式采样是同一类

第 2 章那个"训练模式采样输出乱码"的 bug，在视觉章节同样存在， 但修复在共用的 generate_group() 里，所以这里自动就好了。 这就是把逻辑抽到共用模块的价值。

10如果继续做

这一章的代码是对的，跑不出学习效果是因为配置，不是实现。 三个可量化的调整方向：

问题调整预期效果
撞 512 上限 max_new_tokens 提到 1024 减少截断，但单步耗时翻倍
4 条答案总一样 group_size 提到 8 或 16 更容易采到不同选项，出现混合组
题目对 4B 太简单 换更难的几何数据集，或只跑模型错的题 直接制造组内方差

还有一个更根本的思路：把"截断"本身变成信号。 现在截断的回答 reward 记 0，和"答错"混在一起。 如果加一条规则——没写 boxed 但推理里有正确答案，给部分分—— 退化组就会减少。但这就偏离了原版的可验证 reward 定义，属于设计取舍。

对学习来说，这一章最有价值的是什么

不是"训练成功了"，而是看到一次诚实的负结果： 代码正确、数据正确、模型加载正确，但就是没有训练信号。

真实项目里这种情况非常常见，而大部分教程不会展示。 日志里清清楚楚写着 train_samples = 0、 degenerate = 1.0、format_rate = 0—— 这就是判断"要不要继续调参"的证据。
