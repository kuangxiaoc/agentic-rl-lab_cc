01一句话说清 GRPO

同一道题，让模型自己答 G 次，然后用这 G 个答案的平均分当基准线。 比平均分高的答案被奖励，低的被压制。

关键在于：基准线是模型自己造的，不需要额外训练一个 value model。 这就是 GRPO 相对 PPO 最大的简化，也是它能在单卡上跑起来的原因。

Ai = ri − mean(r1, r2, …, rG) r 是规则打分（本题只有 0 或 1），A 是第 i 条答案的相对好坏。

本项目的 reward 是可验证的：从回答里抠出 \boxed{} 的内容， 和 GSM8K 的标准答案做字符串比较。对就 1，错就 0。没有 reward model，没有人工标注，也没有 API 调用。

为什么这个 reward 靠谱

GSM8K 的答案都是纯数字，比较前只做两步归一化：去掉千分位逗号、去掉结尾句点。 所以 1,000 和 1000 算同一个答案，不会因为格式差异误判。

02训练循环五步

下面这五步就是 local_gpu.py 第 86–139 行的全部内容。 每步都标了行号，你可以对着文件看。

1

取一道题，渲染成 promptL86–93

从 GSM8K 取第 step 题，用 chat template 拼成 3 条 few-shot 示例加当前题目， 再转成 token id。这一段通常是 149 个 token。

2

采样 G 条回答，同时记下采样时的概率L94

model.generate(num_return_sequences=4) 一次生成 4 条。 它同时返回每步的 logits，换算成 log 概率后存为 old_logprobs—— 这是后面算 ratio 的基准。

3

规则打分，再减组内均值L106–107

4 条回答各得一个 0 或 1，然后减去这 4 个数的平均值，得到 4 个 advantage。 这就是上面那个公式。

4

丢掉没有信号的样本L113

if advantage == 0.0: continue。全对或全错的组， 每条 advantage 都是 0，整个 step 直接跳过，不碰权重。

5

重新 forward，算 loss，反向传播L126–138

把 prompt + completion 整段喂回模型，只取 completion 那几位的 log 概率， 和采样时存的对比得到 ratio，再乘 advantage。最后 backward 加 step。

第 2 步和第 5 步是同一个模型

采样时用 model.eval()，训练时切回 model.train()。 不是两个模型，是同一份 LoRA 权重在两种模式下各跑一次。为什么要切，见最后一节。

03真实一组的四个答案

这是 run-20261108-184052 的第 4 步，也是 10 步里唯一真正更新了权重的一步。 题目和 4 条完整回答都来自 samples.jsonl。

GSM8K · step 4

James writes a 3-page letter to 2 different friends twice a week. How many pages does he write a year?

标准答案 624

✗ 错 answer 0 reward 0.0 advantage −0.5
James writes a 3-page letter to 2 different friends twice a week. First, find how many letters he writes per week: - Each week, he writes to 2 friends, and he writes 3 pages per letter. - So, per week: 2 friends × 3 pages = 6 pages. Now, how many weeks in a year? - There are 52 weeks in a year. So, total pages per year: - 6 pages/week × 52 weeks = 312 pages. \boxed{312}
✗ 错 answer 1 reward 0.0 advantage −0.5
... He does this **twice a week**, so: 2 times/week × 6 pages = 6 pages per week? Wait — that's incorrect. Wait! Let's rephrase: He writes a 3-page letter **to each friend**. So each week, he sends: - 2 letters × 3 pages = 6 pages per week. So total pages per year = 6 pages/week × 52 weeks = 312. ✅ Final answer: \boxed{312}
✓ 对 answer 2 reward 1.0 advantage +0.5
First, calculate how many letters he writes per week: - Each week: 2 friends × 3 pages = 6 pages per week. He does this twice a week → So: 2 × 6 = 12 pages per week. Now, how many weeks in a year? Approximately 52 weeks. So total pages per year: 12 pages/week × 52 weeks = 624 \boxed{624}
✓ 对 answer 3 reward 1.0 advantage +0.5
- 2 friends × 2 times per week = 4 letters per week Each letter is 3 pages, so: - 4 letters × 3 pages = 12 pages per week Now, calculate the number of weeks in a year: Assume 52 weeks in a year. So total pages per year: - 12 pages/week × 52 weeks = 624 \boxed{624}
answer 1 最值得看

它中途写出了 "Wait — that's incorrect."，说明模型内部确实意识到漏了「twice a week」。 但它在自我纠正时又回到了同一个错误，把 6 页/周 当成最终结果。

这正是 GRPO 想压制的模式：不是算错，而是推理路径本身有系统性偏差。 answer 2 和 3 走了两条不同的正确路径——一条先算 12 页/周，一条先算 4 封/周—— 它们拿到 +0.5，就是把「正确路径」的概率往上推。

04advantage 怎么算

四个 reward 是 [0, 0, 1, 1]，均值 0.5。每个减 0.5：

r = [0, 0, 1, 1]    mean(r) = 0.5
A = [0−0.5, 0−0.5, 1−0.5, 1−0.5] = [−0.5, −0.5, +0.5, +0.5] 代码：common.group_advantages(rewards)，一行推导，没有任何可学习参数。

这个 0.5 就是 GRPO 的 baseline。它不需要训练，因为它就是从这一组样本里现算出来的。 PPO 要用一个和策略同规模的 value model 去估计同样的东西，那才是 GRPO 省掉的成本。

advantage 会被复制到每个 token 上

一条回答有 N 个 token，这条回答的 advantage 会重复 N 次，作为每个 token 的权重。 代码在 local_gpu.py:120：advantages=[advantage] * len(logprobs)。

这是序列级信用分配：不区分哪个 token 贡献大，整条回答一起奖或一起罚。 简单，但也是 GRPO 的已知局限。

05loss 怎么算

核心只有三行，在 scripts/local_gpu_trainer.py 的 sequence_policy_loss() 里。

scripts/local_gpu_trainer.py · sequence_policy_loss()

# current: 训练时模型对 completion 每个 token 的 log 概率
# old:     采样时模型对同样 token 的 log 概率
ratio = torch.exp(current - old)

loss = -(ratio * advantage).mean()

ratio 就是第 1 章那个概率比例。第一次更新时，current 和 old 是同一份权重算的，所以 ratio ≈ 1。

ratio = exp(current − old) ≈ 1
losstoken = −(1 × advantage) 所以第一次更新时，loss 完全由 advantage 的符号和大小决定。
这一步的 loss 是 −0.0002，接近 0——但它真的学了

组内 advantage 加起来正好是 0（这是均值中心化的必然结果）， 所以 12 个 token 的 loss 加起来也接近 0。

但梯度不是 0：6 个 token 拿到正梯度、6 个拿到负梯度， 它们作用在同一批 LoRA 权重上，方向不同，权重就动了。 看 loss 判断有没有学习会被误导，要看 train_samples 和 reward 分布。

三种 loss 的差别

loss_fn公式行为
importance_sampling -(ratio * adv).mean() 最直接。ratio 不设上限，一次更新可能走太远。本次实验用的就是这个。
ppo -min(ratio*adv, clamp(ratio)*adv).mean() ratio 越界后不再提供梯度，等于「关掉」这条 token 的更新。
cispo -(detach(clamp(ratio)) * current * adv).mean() clip 后当固定砝码，梯度仍来自 logprob，不会完全断电。

06下标与形状

这一段代码最容易看晕，因为它有一个差一位的对齐。看下面这张图就清楚了。

sequence_policy_loss() 里的下标算术

input_ids = prompt + completion        # 149 + 3 = 152 个 token

logits  = model(input_ids).logits[0, :-1]   # 151 个位置
targets = input_ids[0, 1:]                  # 151 个 token

prompt_length = 152 - 3 = 149
completion_positions = slice(149 - 1, 149 - 1 + 3)   # 位置 148, 149, 150

logits[i] 预测的是 input_ids[i+1]。所以：

位置这个位置的 logits 预测属于
147input_ids[148]prompt
148input_ids[149] ← completion 第 1 个 tokencompletion 起点
149input_ids[150]completion
150input_ids[151]completion 末尾
151—（被 :-1 丢掉）没有下一个 token 可预测

prompt_length − 1 = 148 就是 completion 第一个 token 的预测位置。 这就是为什么切片要减 1，不是写错了。

这个 off-by-one 是 LLM 训练里最常见的 bug

写错的话，loss 依然能算出来、也不会报错，只是把 prompt 的 token 也算进了 completion 区间， 训练信号就被稀释了。代码里 completion_positions 这一行值得多看两眼。

degenerate 这个字段就是标记这件事：1.0 表示这一组全对或全错，没有相对信号。 原版 PyTRIO 代码里叫 frac_degenerate，论文里也会专门讨论。

想看到更多训练信号，有三个方向

加大 group_size：4 条全对，采 16 条可能就有错的了。
提高 temperature：现在用 1.0，调高会让答案更分散。
换更难的题：GSM8K 前几题偏简单，后面的题错误率更高。

这三个都是 PROFILES 里的参数，改起来是一行的事。

每步 9–26 秒，绝大部分花在 model.generate 上。 真正训练的那一步只比其它步多几秒。

所以想加速，方向是减少生成 token 数（调小 max_new_tokens） 或者换更快的采样后端（vLLM / SGLang），而不是优化 loss 计算。

10踩过的坑

下面每一条都是在 A10 上真实撞到、修掉、并留下测试的。 它们不是理论问题，是换台机器、换个模型版本就会再出现的问题。

① 训练模式采样，输出全是乱码

现象：reward 全 0，回答是 '\,thimes{costan月tanftyrdimes...' 这种。

原因：训练模式开了 gradient checkpointing，它和 KV cache 互斥。 generate() 每步被强制丢掉 past_key_values， 模型只能看到当前 1 个 token，位置编码却还在往后偏移，于是瞎猜。

修法：采样前 model.eval()，采完 model.train() 切回来。

② 每组采了 16 条而不是 4 条

原因：先把 batch-1 的 prompt 手工 repeat 4 次，又传了 num_return_sequences=4，结果 4 × 4 = 16 条。

修法：直接传 batch-1 的输入，让 generate 自己展开。

③ 下载完 12GB 模型才报 AttributeError

原因：AST 加载器用 ast.literal_eval 过滤常量， 而 FEWSHOT_PREFIX 是 "..." + QUESTION_SUFFIX 拼出来的， 不是纯字面量，被静默丢弃。

修法：改成表达式级安全检测，并让每个章节显式声明依赖的常量， 缺失就在训练开始前失败。

④ huggingface.co 连不上

现象：第 3 章 LocalEntryNotFoundError: Network is unreachable。

修法：默认 HF_ENDPOINT=https://hf-mirror.com，可覆盖。

这些坑都留了回归测试

tests/ 下有 32 个不依赖 torch 的测试， 其中就有「采样必须在 eval 模式」「每组必须恰好 group_size 条」这两条。 改坏了会立刻红。
