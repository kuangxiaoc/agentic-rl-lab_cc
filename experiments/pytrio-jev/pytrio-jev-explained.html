01 · 先看结论

它不是 RL，而是一次极窄的监督

第 04 章把“回答一道题”改成“在一次 forward 里同时做五个固定选项判断”。每个字段只在 decision marker 前一个位置计算 loss，推理时也只读候选符号的 logits。

34.4%250 个决策中答对 86 个。训练 loss 明显下降，但这只是 50 条测试记录的局部结果。
这一章最值得记住的实验事实

训练最后一步的 marker accuracy 是 60%，但测试集总体只有 34.4%。单条记录的 batch loss 很小，不等于模型已经学会稳定的决策规则。

03 · 符号与公式

模型不是“说出答案”，而是给候选 token 打分

一条训练记录会先被渲染成 chat 文本。assistant 侧不是完整答案，而是类似 {"action":"decision","risk":"decision"} 的 JSON 骨架；每个 decision 是单独一个 token。训练时把目标符号 token 的 id 填在 marker 的前一个位置，让模型在那个位置预测它。原始 PyTRIO 代码在 Datum 中明确使用同一坐标；本地训练也按这个坐标构造 labels。

  • x整段输入，包括 state、问题说明、固定选项和 JSON 骨架。
  • m某个字段的 decision marker 在 token 序列中的位置。
  • am该字段正确答案对应的符号 token，例如 A、yes 或 1。
  • zv模型在位置 m−1 给词表第 v 个 token 的原始分数，也就是 logit。
  • p(am | x)softmax 后，模型给正确符号的概率。
  • −100PyTorch cross entropy 的忽略标记；这些位置不参与 loss，也不产生梯度。
p(am | x) = exp(zam) / Σv exp(zv)
训练时在完整词表上做 softmax。答案 token 的概率越高，cross entropy 越小。
LCE = −(1 / M) Σm=1..M log p(am | x)
M 是一条记录里真正被监督的字段数。40 steps 的 batch size 都是 1，所以每步只来自一条记录。

代码把 labels 全部初始化成 −100，只在每个 marker 前一个位置填入答案 token id，然后调用标准的 cross_entropy(..., ignore_index=-100)。因此一条很长的记录也只会在几个位置产生 loss。

为什么是 marker 前一个位置

自回归模型在位置 t 的 logits 预测位置 t+1 的 token。代码要让位置 marker−1 的预测目标是答案符号，所以把 label 填在那里；推理时也从同一个位置读取 logits。marker 本身只负责定位字段，答案符号并不出现在输入中。

04 · 完整训练链路

从 parquet 到一次 LoRA 更新，中间发生了什么

typed-decisionsstate + questions + gold
→
compile固定选项与符号
→
chat + skeleton写入 decision marker
→
one forward所有字段共享上下文
→
masked CEbackward + optimizer.step
for one record:
  ids, markers = tokenize(state, schema, skeleton)
  labels[:] = -100
  for field, gold_symbol in targets:
      labels[markers[field] - 1] = symbol_id(gold_symbol)

  logits = model(ids).logits
  loss = cross_entropy(logits, labels, ignore_index=-100)
  loss.backward()
  clip_grad_norm_(trainable_lora_parameters, 1.0)
  optimizer.step()

  save metrics: loss, marker_accuracy

marker_accuracy 只检查被监督位置上的 argmax 是否等于 gold token。它是训练 batch 内的对齐指标，不是 250 个测试决策的准确率。40 steps 结束后，才把 adapter 挂到 base 上，对 50 条 test 记录逐个字段评测。

为什么曲线会抖

这不是常规的大 batch 训练。每一步只更新一条记录，marker accuracy 是该记录内几个字段的比例。它的主要作用是确认 marker 对齐和梯度链路，不是估计泛化能力。

08 · 机制

标签只落在 marker 前一个位置

input:  ... "action": "decision" ...
labels: ...          ↑ 只在这里填答案 token
                        其余位置 = -100

eval:
  logits[marker - 1]
      ↓ index_select(合法候选符号)
      ↓ softmax
  prediction = argmax

这就是“决策模型”和普通 SFT 的差别。普通 SFT 要模型写完整答案；这里只要求它在固定位置从有限候选里选一个。所有字段共享 state，但答案不出现在输入中，因此字段之间不会看到彼此的标签。

09 · 真实数据手算

置信度 0.532 时，正确答案的 CE 是多少？

先算一个“答对”的字段

  1. 第一条记录的 outcome 答对了，评测置信度是 0.5318。
  2. 如果把这个候选 softmax 概率近似当作正确符号概率：−ln(0.5318) ≈ 0.631。
  3. 这表示模型并非“非常确定”；即使 argmax 正确，概率也只比一半多一点。

但训练 loss 用的是完整词表上的 cross entropy，不是评测时只在候选符号上重算的概率。因此 0.631 只能帮助理解 CE 的量级，不能和 history 里的 batch loss 逐项对齐。

再看一个“答错但很自信”的字段

  1. urgency 的预测置信度是 0.7723，但 gold 是另一个符号。
  2. 日志只记录“预测符号的概率”，没有记录“错误 gold 符号的概率”，所以不能直接算出这个字段的真实 CE。
  3. 已知的是：模型把 77.23% 的候选概率给了错误答案，说明错误不是低置信度抖动。

50 条记录上，答对字段的平均置信度约 0.7755，答错字段约 0.7397。两者很接近，说明这些分数没有被温度校准，不能直接把 0.8 当作“八成正确率”。

11 · 常见疑问

几个最容易卡住的点

为什么说它不是 RL？

因为没有 rollout、reward、advantage 或 policy ratio。它是有监督学习：每个字段都有固定 gold 符号，直接最小化正确符号的 cross entropy。模型参数更新了，不等于任务自动变成强化学习。

五个字段为什么能在一次 forward 里完成？

整段 state、问题说明和 JSON 骨架一起进入模型；每个字段的 decision marker 都在这条序列中，只是 label 落在不同位置。一次前向就得到所有位置的 logits，不需要为每个字段各跑一次模型。

训练时和推理时都在候选符号上 softmax 吗？

不是。训练直接对完整词表计算 cross entropy，答案是某个符号 token；推理为了只比较合法选项，才从完整 logits 中取出候选符号，再在候选集合上重新 softmax。

为什么 loss 从 18 降到 1 左右，测试准确率仍只有 34.4%？

训练每步只有一条记录，模型可以快速适配当前样本的格式和局部模式；测试集换记录后还要泛化到新的 state。训练 loss、训练 marker accuracy 和 held-out 决策准确率回答的是三个不同问题。

置信度能直接用于业务阈值吗？

不能直接使用。答对和答错的平均置信度太接近，说明概率没有校准；要用于放行或人工复核，需要在独立校准集上拟合温度或别的校准方法，并报告 ECE、覆盖率与错误率。

34.4% 能代表原版 Jev 的效果吗？

不能。这里是 40-step smoke、单条 batch、typed-decisions 的 50 条 test 记录，也没有 ToolACE、Jevbench 全套评测和温度校准。它验证的是机制与产物链，不是论文表格的等价复现。
